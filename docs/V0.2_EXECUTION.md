# impactctl v0.2 execution plan

v0.2 moves `impactctl` from **repository impact** to **service impact** while preserving the v0.1 principles: deterministic, explainable, local-first and useful without a hosted control plane.

## Execution order

### Phase A — service model foundation

**#8 — service-map configuration schema**

Deliver `.impactctl.yml` parsing, validation, path-to-service mapping, criticality and owner metadata. Existing v0.1 behavior must remain unchanged when the file is absent.

This is the dependency for the rest of v0.2.

### Phase B — direct contract impact

**#9 — OpenAPI consumer/provider impact**

Use the service map to connect changed OpenAPI contracts to configured providers and consumers. Relationships must be explicit; `impactctl` must not invent dependencies.

Depends on #8.

### Phase C — downstream blast radius

**#11 — dependency-aware downstream impact**

Traverse explicit service dependencies and report direct and transitive impact with a deterministic path for every affected service. Cycles must terminate safely and produce stable output.

Depends on #8 and should build on the service-impact model established by #9.

### Phase D — event contracts

**#10 — AsyncAPI event-schema impact**

Add event-contract evidence and additive/breaking classification where the tool can do so safely. Uncertain semantic cases must remain explicit instead of being guessed.

Depends on #8 and can progress in parallel with #9/#11 once the service-map schema is stable.

### Phase E — specialist semantic interoperability

**#12 — optional `oasdiff` adapter**

Normalize specialist OpenAPI semantic findings into the `impactctl` evidence model while preserving provenance. `oasdiff` remains optional; the core must continue to work without it and without network access.

Best implemented after #9 so the adapter can feed an already-stable provider/consumer impact model.

## Scope decision (2026-09-26)

The optional `oasdiff` adapter (#12) is **deferred beyond v0.2**; it is not required to use the existing explicit OpenAPI provider/consumer service-impact functionality. README and CHANGELOG document this boundary. External multi-service dogfood issue #15 was completed and merged in PR #29, with pinned source and CI evidence in `docs/validation/V0.2_EXTERNAL_CANDIDATE.md`.

## v0.2 release gate

A `v0.2.0` release is ready when all of the following are true:

- #8–#12 are closed, or an item is explicitly moved out of v0.2 with the roadmap and changelog updated.
- Running without `.impactctl.yml` preserves v0.1 behavior.
- Repeated runs against the same repository state produce deterministic ordering, scores and evidence.
- Human, JSON and Markdown outputs expose the same core service-impact facts.
- Golden fixtures cover at least linear, branching and cyclic service graphs.
- At least one real repository is used as a dogfood validation target in addition to synthetic fixtures.
- No relationship is inferred when configuration does not declare it.
- The core path remains local-first and requires no network service.
- GitHub PR-comment safety guarantees from v0.1 are not weakened.
- CI, release packaging, version injection and checksum generation are green.
- README and changelog describe the v0.2 service-impact model and upgrade path.

## Architectural boundary

`impactctl` owns:

**change → evidence → service relationships → downstream system impact**

It should interoperate with specialist analyzers for deep domain semantics rather than reimplementing every semantic rule surface itself.

## Working rule

Do not add heuristics that silently create service relationships. Explicit evidence is preferred over apparent intelligence. When the tool cannot know safely, it should say so.
